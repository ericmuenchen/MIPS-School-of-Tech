Course Description

Web Design and Dev II is the second semester of the Web Design pathway and continues directly where Web Design and Dev I left off. Last semester you learned to write HTML and CSS by hand and published a live portfolio. This semester is about building sites other people can actually use: sites that fit any screen, that lean on professional tools instead of starting from nothing, and that get better because you tested them with real people.

The semester runs through five units. You’ll open by bringing your animated “Tell a Story” page into your portfolio, then learn Bootstrap: page layouts, open-source components, navigation bars, the grid system, and mobile responsive design. You’ll put that to work in a team Bootstrap project, study user-interface design (accessibility, readability, user research, and prototyping), and close with a final project you scope, design, prototype, test, and build from scratch.

How This Course Works

This is an asynchronous online course delivered through CodeHS, where you’ll write and publish your code right in the browser, with nothing to install. Each unit is broken into lessons made of short video tutorials, quick quizzes, example pages to explore, and hands-on exercises where you build and publish your own sites. Assignments, feedback, and announcements live in Google Classroom. Two of this semester’s units are team projects, so a few weeks will ask you to coordinate with classmates as well as work at your own pace. Keep up with the weekly checkpoints on the schedule so projects don’t stack up.

Use Chrome for the best experience

Browsers render HTML and CSS a little differently, so do your coding in an up-to-date version of Google Chrome. It’s free, and it’s what the CodeHS editor is built and tested against.

What You'll Learn

Build with Bootstrap

Read the documentation and use open-source components, navigation bars, and the grid to lay out a page fast.

Design for Every Screen

Build mobile responsive sites that stay readable from a phone to a wide monitor.

Design for People

Research the people you are building for, write a clear problem statement, and judge an interface for accessibility and readability.

Prototype and Test

Sketch on paper, test with real users, and improve the design before you write a line of code.

Grading

Your grade is built from lesson exercises, unit quizzes, and the projects you design, test, and publish, weighted toward the work you build and revise. These are the graded pieces this semester:

  1. “Tell a Story” portfolio page
  2. Bootstrap exercises
  3. Bootstrap Team Project
  4. User research & prototypes
  5. UI Design Project
  6. Final Project
  7. Lesson & unit quizzes

Course Policies

Pacing & deadlines

The course is self-paced, but the schedule’s weekly checkpoints keep you on track to finish the semester. If you fall behind, don’t panic: message me and we’ll make a plan to catch up. Steady weekly progress beats last-minute cramming every time.

Late work & revision

Late work is accepted: getting it right matters more than getting it in first. Because coding is about iteration, you may revise and resubmit exercises and projects to improve your grade. Growth counts here more than penalties.

Team projects

Units 8 and 10 are built with a team. In an asynchronous course that takes a little planning: we’ll agree on who owns which pages and how you’ll keep in touch before the building starts. If a teammate goes quiet, tell me early rather than absorbing their work in the last week.

Communication

Email me or book a 1:1 through the scheduling link above; I usually reply within one school day. Lessons and exercises live in CodeHS, and feedback, grades, and announcements live in Google Classroom; check both regularly.

AI Policy

The goal is for you to be able to write and understand the code.

AI tools can explain a concept or help you find a bug, and used that way they’re a great tutor. But if the tool writes the page for you, you haven’t learned to build web pages, which is the entire point of this course. Lean on AI to understand, not to replace the work.

  • You may use AI to explain concepts, define terms, or help you understand an error message.
  • Do not paste AI-generated HTML or CSS in as your own: submitted code should be code you can read and explain.
  • I may ask you to walk me through how your project works; if you built it, that’s an easy conversation.
